# ADR 0001：Agent Host 与 digital-employee 的双运行时边界

- 状态：已接受
- 日期：2026-08-03
- 决策范围：`digital-employee` 的产品边界、运行时边界与后续演进方向

## 背景

`digital-employee` 需要让开发者在 Claude Code、Qoder CLI、Codex 等现有 Agent 环境中构建和运行数字员工，同时也要把同一个员工包装成可长期在线的服务。两类环境解决的问题不同：现有 Agent host 已经拥有模型推理、工具调用和多轮执行能力；一个长期运行的数字员工还需要通道接入、任务排队、权限策略、审计和进程生命周期等服务能力。

如果 `digital-employee` 再实现一套通用 Agent loop，会同时面临两类问题：一是重复建设宿主已经提供的推理与工具循环，难以持续跟上各宿主能力；二是把钉钉接入、知识同步、会话和安全控制混进模型循环，最终形成难以移植的单体机器人。

## 决策

采用“双运行时”架构：

1. **内层 Agent host 运行时**由 Claude Code、Qoder CLI、Codex 等宿主提供，负责模型推理、原生工具循环、上下文消费和增量事件输出。
2. **外层 digital-employee 运行时**负责员工包规范、Host Adapter、通道接入、ACK、去重、队列、会话生命周期、策略执行、审计、可观测性和服务包装。

`digital-employee` 的 CLI 是这套架构的权威入口：用于初始化、校验、诊断、运行和包装员工项目，而不是成为另一个通用大模型终端。

首个落地实现是 `run --engine qoder`：只支持 Qoder CLI 1.1.x、无状态新会话、只读本地资产，暂不开放 MCP、附件、写操作和审批回调。它通过最小投影目录、隔离配置、工具收窄和 `system/init` 运行时校验实现边界；Adapter 会显式启用 SDK process mode，要求协议主版本兼容且 skills/plugins 明确为空，再把 SKILL 与任务经 `initialize → user → EOF` 的 stdin JSONL 协议传递，不进入 Qoder 参数向量。Claude Code 与 Codex 当前仍只有探测。

现有自研 `model + retriever + employee` 执行循环冻结为 **`standalone-v1` 兼容层**。它继续支撑无外部 Agent host、无模型凭证的控制台演示和既有配置，但只接受必要的兼容修复、安全修复和可观测性修复；新的宿主能力、工具编排能力和员工模板不再优先扩展到该循环。

## 运行时边界

### 内层 Agent host 负责

- 根据系统指令与任务上下文进行推理；
- 执行宿主原生的工具调用循环；
- 管理单次执行中的上下文窗口与工具结果；
- 输出可被适配器解析的文本、工具、状态、用量和错误事件；
- 响应取消、超时和宿主自身的执行限制。

### 外层 digital-employee 负责

- 定义并校验数字员工包；
- 选择、探测和调用 Host Adapter；
- 把抽象权限映射为宿主的实际工具和目录权限；
- 管理消息通道、立即 ACK、去重、并发、排队、重试和优雅退出；
- 编排允许使用的知识快照、会话记忆和人工升级路径；
- 归一化宿主事件，执行输出清洗、审计和运行指标采集；
- 把员工包装成本地进程、受控服务器进程或合规沙箱中的服务。

外层运行时不接管宿主内部的思维过程，也不要求记录或暴露 chain-of-thought。审计只保存任务输入摘要、策略决策、工具调用元数据、来源引用、状态、用量和最终输出等必要信息。

## DWS 答疑机器人的证据

`dws-workbench` 中的答疑机器人验证了双运行时模式：

- `server/dingtalk-agent/standalone.js` 和 `index.js` 构成长期在线的外层服务，负责钉钉 Stream、ACK、去重、排队、附件、回复和进程生命周期；
- `server/dingtalk-agent/analyzer.js` 的 `runAnalysis()` 没有实现新的模型推理循环，而是启动 Claude Code 或 Qoder CLI，并解析两者的流式 JSON 事件；
- `server/ecosystem.config.cjs` 用 PM2 把钉钉入口包装成长运行进程，进一步说明“服务生命周期”和“Agent loop”是两层；
- 只读边界最终由宿主启动参数收窄到 `Read`、`Grep`、`Glob`，而不是只依赖 Prompt 声明；
- `memory.js`、`session.js`、`repo.js`、`community.js` 和 `connection.js` 分别承担 FAQ、短期会话、代码快照、离线知识和连接自愈，这些都是外层服务职责；
- `buildIndex.js` 会读取目标仓库的 `SKILL.md` 作为领域知识，但在线执行时并不开放宿主的 Skill 工具，说明“可移植知识说明”和“宿主执行机制”应解耦。

该实现同时暴露了不能直接复制的部分：DWS 身份、回答规则和专家名单集中在一个大 Prompt 中，索引器硬编码了 DWS 的目录结构，宿主选择依赖不断增长的条件分支，通道与领域逻辑也集中在单个消息处理函数中。这些代码适合作为行为证据和参考 recipe，不作为 `digital-employee` 的核心抽象。

## 可移植员工包

员工包的规范来源保持宿主中立，核心由三部分组成：

1. **`SKILL.md`**：描述员工角色、任务边界、工作方法、知识使用顺序和人工升级规则；
2. **MCP**：描述可调用能力及其输入输出契约，把文档、网盘、DWS 等能力作为显式 connector/tool 接入；
3. **Schema**：约束员工清单、任务输入、最终输出、事件、权限和配置版本。

Prompt、宿主配置文件和启动参数是员工包面向某个 host 的投影或构建产物，不是唯一事实源。Host Adapter 可以把同一份员工包转换为宿主支持的指令、MCP 配置、工作目录和权限参数，但不得反向要求核心清单包含某个厂商专属字段。

员工包可以包含 `prompts/`、`knowledge/`、`policies/`、`evals/` 和通道配置；这些扩展都必须通过清单和 Schema 声明，不能靠扫描任意目录获得隐式权限。

## Host Adapter 与能力协商

每个 Host Adapter 必须实现统一的探测与执行契约，至少报告：

- host 标识、版本和非交互执行方式；
- 安装探测必须与运行前 preflight 分离；只有宿主能安全检查时，preflight 才报告认证是否可用，并且不得返回凭证内容；
- 事件协议及支持的事件类型；
- 工具白名单是“真正收窄”还是仅“追加允许”；
- 可授权的工作目录和附加目录能力；
- 是否支持 MCP、附件、取消、超时、用量和成本事件；
- 当前执行边界是本地进程、远端服务还是受控沙箱。

员工清单声明运行所需能力，`digital-employee validate` 做静态校验；带 `--engine` 时还执行与真实运行一致、但不调用模型的包级 preflight，再把需求与实际能力进行协商。只有全部必需能力都能被宿主强制执行时，任务才可以启动。

归一化事件协议至少覆盖 `run.started`、`assistant.delta`、`tool.started`、`tool.completed`、`run.completed`、`run.failed` 和 `usage`。Adapter 负责处理不同宿主的原生事件差异，核心运行时不得直接解析某一宿主的专有流格式。

## Fail-closed 与安全要求

- 宿主缺失、版本不兼容、认证不可用或能力协商失败时，默认拒绝启动；
- 不允许从“工具强制白名单”静默降级为“仅在 Prompt 中要求只读”；
- 如果宿主的 allow-list 只会追加能力而不能收窄默认工具集，该宿主不满足只读员工要求；
- 不允许在未声明的 host 失败后自动切换到另一个 host 或 `standalone-v1`，除非员工清单显式声明且两个执行路径满足同一策略；
- 工作目录、附加目录、MCP Server 和知识源必须使用显式 allowlist；路径解析后仍需位于授权边界内；
- 凭证由部署环境或宿主安全存储提供，不进入员工包、日志、审计事件或生成产物；
- 写工具需要独立的审批策略和隔离执行环境，不属于首个版本的默认能力；
- 任何带文件或工具能力的远端部署都必须运行在能提供隔离、审计和资源限制的环境中，不能因为更换 Agent CLI 而绕过部署安全边界。

## WorkBuddy 定位

当前暂把 WorkBuddy 视为**上层工作台或上下文网关**，而不是与 Claude Code、Qoder CLI、Codex 对等的 Agent host。它可以创建项目、提供上下文、调用 `digital-employee` CLI，或承载员工管理入口，但不直接进入 Host Adapter 列表。

只有当 WorkBuddy 能稳定提供非交互执行、标准事件、取消、工具权限收窄、目录授权和能力探测等契约时，才重新评估其是否成为对等 host。该判断基于能力契约，不基于产品名称或交互界面。

## 迁移步骤

1. 冻结并标记当前执行循环为 `standalone-v1`，保留现有控制台演示和配置兼容性；
2. 定义员工包 Schema、标准运行事件和 Host Adapter 接口；
3. 实现 host 探测与能力协商，先接入一个可以强制只读的 CLI host；
4. 把通道、队列、会话、策略、审计和升级路径从具体 answer-agent 中抽到外层运行时契约；
5. 将 `profiles/answer-agent` 改造成第一个可移植 recipe，以 `SKILL.md + MCP + Schema` 为规范来源；
6. 用同一份员工包接入第二个 host，验证核心清单不需要厂商分支；
7. 提供静态校验、host 诊断、最小回放集和安全验收，确认只读策略、取消、超时和输出净化在不同 host 上行为一致；
8. 在新路径稳定后，再评估 `standalone-v1` 的长期支持周期，不在本 ADR 中决定删除时间。

迁移期间，权威兼容入口是 `legacy ask|sync|start|serve`；既有顶层名称在 `0.x` 保留为带明确警告的别名，stdout、参数和退出码保持兼容。新路径必须显式选择 host，Host 失败时绝不自动进入 `standalone-v1`。Agent-native 长运行入口未来使用独立的 `service start` 命名；在它交付前，现有 `legacy serve` 不能被描述为新架构的托管服务。

## 影响与权衡

采用双运行时后，`digital-employee` 可以复用宿主持续演进的 Agent 能力，并让同一个员工包在不同宿主间迁移；通道、策略和审计也能独立测试。代价是需要维护多套 Host Adapter，并处理不同宿主在事件、权限和登录方式上的差异。

该代价通过能力协商、标准事件和 fail-closed 控制。我们接受“部分宿主暂时不可用”，不接受为了表面兼容而降低安全边界。

## 非目标

本决策不包含：

- 自研一个替代 Claude Code、Qoder CLI 或 Codex 的通用 Agent loop；
- 复制 DWS 答疑机器人的大 Prompt、专家名单、目录硬编码或宿主条件分支；
- 在当前仓库实现机器人市场、租赁、动态定价、计费和分账；
- 把 `design-system` 当作员工运行时，或在本阶段建设完整 Web Studio；
- 自动安装、授权或代管第三方 Agent host 的账号与许可证；
- 默认开放写文件、执行 Shell 或调用有副作用的业务工具；
- 承诺任意 Agent host 都能无条件部署到普通服务器。

## 重新评估条件

出现以下情况之一时重新评估本决策：主流 Agent host 不再提供可自动化的执行接口；能力差异导致员工包无法保持稳定的宿主中立语义；或 `standalone-v1` 成为明确的产品主路径而不再只是兼容需求。重新评估前仍以本 ADR 的边界为准。
